## 1. What USRP Is

USRP is a single national digital recruitment platform for Rwanda's three
security organs:

| Agency | Full name | Domain |
|--------|-----------|--------|
| **RDF** | Rwanda Defence Force | Military |
| **RNP** | Rwanda National Police | Police |
| **RCS** | Rwanda Correctional Service | Corrections |

**The problem it solves.** Recruitment today is manual: eligibility and identity
vetting, certificate checks, and criminal-record clearance take weeks and are
error-prone. USRP turns that into a streamlined digital pipeline — one applicant
profile, instant identity/eligibility verification against government systems, and
three isolated agency back-offices.

**The two hard invariants** — everything else serves these:

1. **Cross-agency isolation.** An RDF officer must never see an RNP-only
   applicant. This is enforced at the *database engine* (PostgreSQL FORCE'd RLS),
   not in application code. A citizen who cross-applies is the only shared case.
2. **Citizen data protection.** The system holds PII, biometrics metadata, and
   criminal-record status under **Rwanda Law N° 058/2021**. PII is encrypted at
   rest; the raw National ID is *never* stored; biometrics are never stored (only
   scores). See §8.

## 3. System Architecture

Three tiers, event-driven, microservice back-end.

```
        ┌─────────────────────────────────────────────────────┐
Tier 1  │  Public Frontend:  Web portal  ·  USSD  ·  Kiosk     │
        └───────────────────────────┬─────────────────────────┘
                                     │
        ┌───────────────────────────▼─────────────────────────┐
Tier 2  │  API Gateway (Kong)  →  Agency BFFs  →  Microservices│
        │  Identity · Eligibility · Biometric · Forensics ·    │
        │  Vetting · Routing · Scheduling · Notification ·     │
        │  Field-Sync · Audit                                  │
        │            │  event backbone: Apache Kafka  │        │
        └───────────────────────────┬─────────────────────────┘
                                     │
        ┌───────────────────────────▼─────────────────────────┐
Tier 3  │  PostgreSQL (schema-isolated + RLS)  ·  Redis  ·     │
        │  MinIO (encrypted docs)  ·  G2G: NIDA/NESA/HEC/RIB   │
        └─────────────────────────────────────────────────────┘
```

**Style.** Microservices communicate asynchronously over Kafka using immutable,
versioned events (§9). Synchronous reads go through per-agency BFFs. Services
own their logic but share one database *cluster* partitioned by schema (§7) — the
isolation is enforced centrally so it cannot be forgotten by a service.

**Why this shape** — see the ADRs (§10): Kafka over RabbitMQ, schema isolation
over separate databases, CRDT for offline field sync, layered document forensics.

## 4. The Domain Model

*Ground truth: `packages/shared-types`. Ground truth for the types is the official
agency recruitment announcements (RDF May 2026; RNP May/Oct 2025; RCS Aug 2025 /
Jun 2026).*

### Agencies & channels
- **Agencies:** `RDF`, `RNP`, `RCS`.
- **Channels:** `WEB`, `USSD`, `IREMBO_KIOSK`, `WALK_IN`.
- **Walk-in policy** is agency-specific: **RDF allows walk-in** on exam day; RNP
  and RCS require registration during the window (`WALKIN_POLICY`).

### The 10 application categories
Each has its own minimum education and age band (`*_APPLICATION_CATEGORIES`):

- **RDF:** `GENERAL_ENLISTMENT` (18–25), `RESERVE_FORCE_ALEVEL` (18–25),
  `RESERVE_FORCE_UNIVERSITY` (18–26), `RESERVE_FORCE_SPECIALIST` (18–27).
- **RNP:** `CADET_OFFICER` (18–25), `BASIC_POLICE_COURSE` (18–25).
- **RCS:** `GENERAL_ENLISTEE` (18–25), `OFFICER_ONE_YEAR` (18–25),
  `OFFICER_ONE_YEAR_SPECIALIST` (18–27), `OFFICER_FOUR_YEAR_UR` (18–21).

Specialist/priority fields (e.g. `MEDICINE`, `ENGINEERING`, `NURSING`) drive age
exceptions and priority. Geography is modelled exactly (5 provinces, 30 districts,
`DISTRICT_TO_PROVINCE`) because home district drives exam-slot assignment.

### Application lifecycle (`ApplicationStatus`)
Two paths:

- **Path A — pre-registered digital:** `DRAFT → SUBMITTED → ACADEMIC_VETTING →
  CRIMINAL_CLEARANCE → DOCUMENT_REVIEW_{GREEN|AMBER} → SLOT_ASSIGNED →
  PHYSICAL_TEST_SCHEDULED → PHYSICAL_TEST_COMPLETE → MEDICAL_REVIEW →
  FINAL_SHORTLIST → ACCEPTED | REJECTED | WITHDRAWN`.
- **Path B — walk-in (RDF only):** `WALK_IN_REGISTERED → WALK_IN_ON_SITE_VETTING
  → WALK_IN_PHYSICAL_TEST → WALK_IN_REJECTED`.

### Documents
Green/Amber/Red lanes: `PENDING_UPLOAD → UPLOADED → VIRUS_SCAN_PASS →
FORENSICS_{GREEN|AMBER|RED}`, or `VERIFIED_VIA_API` when checked directly against
NESA/HEC (the "green lane" — no forensics needed).

## 5. The Five-Stage Recruitment Pipeline

The applicant journey, and which service owns each stage:

1. **Identity & eligibility (instant)** — NID → NIDA lookup → age/eligibility gate.
   *identity-service, eligibility-service.*
2. **Educational verification** — A-Level via NESA, degrees via HEC.
   *eligibility-service (+ G2G).*
3. **Criminal clearance** — asynchronous RIB / MoJ check.
   *background-vetting-service.*
4. **Documents & biometrics** — upload → virus scan → forensics; liveness + 1:1
   face match. *document-forensics-service, biometric-service.*
5. **Scheduling & field capture** — exam slot by district; offline tablet score
   capture with conflict-free sync. *scheduling-service, field-sync-service.*

Cross-cutting: *routing-service* (agency routing / cross-application),
*notification-service* (SMS/email/USSD), *audit-service* (immutable trail).

## 7. Data Layer

*Ground truth: `packages/shared-database`. Empirically verified against a live
PG16 instance — see `docs/architecture/data-layer-verification.md`.*

### Schema isolation (ADR-002)
One PostgreSQL cluster, five schemas: `public_core` (shared identity, campaigns,
venues, sessions), `rdf_ops`, `rnp_ops`, `rcs_ops` (per-agency applications, docs,
scores), and `audit_log` (append-only).

### Role model — the single source of truth
The application connects as **one privilege-less login, `usrp_app`**, which holds
membership in group roles and assumes one per request via `SET ROLE` (or
`SET LOCAL ROLE` inside a transaction):

- `usrp_system_service` — cross-agency workers (vetting, identity creation). Sees
  all applicants. Holds `SELECT, INSERT, UPDATE` on `applicant_identities`.
- `usrp_rdf_officer` / `usrp_rnp_officer` / `usrp_rcs_officer` — one agency each;
  `SELECT, UPDATE` only. Can resolve a shared identity **only** if that applicant
  has an application in *their* agency's ops schema.

Defined and enforced in `src/rls/0001_roles_grants_rls.sql`.
> ⚠ Two older, divergent role expressions still exist in the repo
> (`init-scripts/02-create-roles.sql`, `.env.example`). The live DB and the
> isolation proof use `0001`. Adopt `0001`; reconcile the other two (§15).

### Row-Level Security
`public_core.applicant_identities` has RLS **ENABLED and FORCE'd** (so even the
table owner is constrained). Policies: `pc_ai_system` (system sees all);
`pc_ai_{rdf,rnp,rcs}` (officer sees an identity only if a matching application
exists in their ops schema). This is *the* cross-agency leak surface, so it is the
one thing proven by a committed regression test: `src/rls/verify-isolation.sql`
(transactional, rolls back, exits non-zero on any leak).

### PII encryption at rest
PII columns (`encrypted_full_name`, `_date_of_birth`, `_home_district`,
`_home_province`) store `pgp_sym_encrypt(plaintext, current_setting('app.encryption_key'))`.
The key is set **transaction-local** (`set_config(..., true)`) so it never leaks
onto a pooled connection. Non-PII from NIDA (gender) is stored plaintext for query
performance. Erasure (Law N° 058/2021) is the **soft-delete** path (`deleted_at`),
not hard delete — no app role has `DELETE`.

### The two-hash contract (do not conflate)
Two different HMAC-SHA256 hashes of the same National ID:

| Hash | Key | Purpose |
|------|-----|---------|
| **Internal `nationalIdHash`** | USRP-private `NATIONAL_ID_HMAC_KEY` | System-wide applicant key, stored in DB, used across services |
| **NIDA-lookup hash** | NIDA-shared secret | Sent to NIDA for lookup; lives only inside the NIDA gateway |

The raw NID is a secret: never stored, never logged, never in an event.

## 8. Security & Compliance

- **Legal basis:** Rwanda Law N° 058/2021 (data protection). The system handles
  citizen PII, biometric metadata, and criminal-record status.
- **PII:** encrypted at rest (§7); raw NID never persisted; erasure via soft-delete.
- **Biometrics:** raw frames/vectors never stored — only liveness and match
  *scores*. The live face vector is sent to NIDA for 1:1 match; NIDA returns a
  score.
- **G2G calls** (NIDA, NESA, HEC, RIB) are HMAC-signed over a canonical request
  string with a timestamp for replay protection (`shared-security/g2g.ts`,
  default 5-min skew window). Real government access requires actual authorization;
  the mocks in `infrastructure/docker/mocks` are **dev-only**.
- **Key management:** dev keys come from env (≥32-char floor enforced by
  `shared-config`). Production keys come from an HSM/KMS. The `app.encryption_key`
  and `NATIONAL_ID_HMAC_KEY` are the crown jewels — a weak key here weakens every
  encrypted column and every applicant key.
- **Field integrity:** offline tablet scores are Ed25519-signed per device
  (`shared-security/signing.ts`) and reconciled with vector clocks (ADR-003).
- **Accountability:** decisions with legal/compliance weight stay with the owner
  and the agencies. Engineers **flag** authorization/compliance limits as they
  arise; they do not decide them.

## 9. Event Backbone

*Ground truth: `packages/shared-events` + `shared-types/events.types.ts`. ADR-001.*

Apache Kafka in KRaft mode (no Zookeeper). Services depend on the **`EventBus`
interface**, never on kafkajs directly (`InMemoryEventBus` for tests/local,
`KafkaEventBus` for prod). **The backbone is proven end-to-end against a live
broker** — a `KafkaEventBus` publish→consume round-trip and an event-driven
service reaction (`APPLICANT_SUBMITTED` → eligibility age gate → `AUDIT_ENTRY`),
with correlation/causation preserved across the wire. See
`docs/architecture/kafka-backbone-proof.md`. In dev, the broker exposes a host
listener on `localhost:29092` (in-cluster: `kafka:9092`).

**Envelope.** Every event carries `eventId`, `eventVersion` ('1.0'), `occurredAt`,
and a **correlation/causation** pair: `correlationId` traces one applicant's
request across all services; `causationId` is the id of the event that caused this
one. Helpers: `newCorrelationContext()`, `deriveContext(parent)`, `newEnvelope(ctx)`.

**Topics & routing** (`shared-events/topics.ts` — exhaustive over the event union,
so an unrouted event type is a *compile* error):

| Event type | Topic |
|-----------|-------|
| `APPLICANT_SUBMITTED` | `applicant.submitted` |
| `NIDA_VERIFICATION_COMPLETED` | `vetting.nida` |
| `NESA_VERIFICATION_COMPLETED` | `vetting.nesa` |
| `HEC_VERIFICATION_COMPLETED` | `vetting.hec` |
| `RIB_VETTING_COMPLETED` | `vetting.rib` |
| `BIOMETRIC_VERIFICATION_COMPLETED` | `biometric.result` |
| `SLOT_ASSIGNED` | `slot.assigned` |
| `FIELD_SCORE_CAPTURED` | `field.score.captured` |
| `AUDIT_ENTRY` | `audit.immutable` |

Partition key = the applicant (or application/entity) id, so all events about one
applicant keep per-applicant ordering across the vetting pipeline.

## 10. Architecture Decision Records

The *why* behind the hard choices. Read these before challenging a foundation.

- **ADR-001** — Apache Kafka (KRaft) over RabbitMQ for event streaming.
- **ADR-002** — PostgreSQL schema isolation + RLS over separate databases.
- **ADR-003** — CRDT (Automerge) + Ed25519 + vector clocks for offline tablet sync.
- **ADR-004** — C2PA + DCT frequency analysis (not ELA-only) for document forgery,
  to withstand AI-generated documents.
- **ADR-005** — service HTTP transport: a zero-dependency `node:http` substrate
  (`@usrp/shared-http`) over a framework (NestJS), consistent with the minimal
  supply-chain principle; reversible at the adapter layer. **Accepted.**

New foundational choices get a new ADR. Don't bury them in code.

## 11. Shared Packages

Six workspace libraries under `packages/`. Design ethos: **minimal supply-chain
surface** for a national-security system.

| Package | What | Runtime deps |
|---------|------|--------------|
| `@usrp/shared-types` | Domain types, event & topic definitions, enums | none |
| `@usrp/shared-security` | NID/phone hashing, Ed25519 signing, G2G signing, AES-GCM | **zero** (Node built-ins only) |
| `@usrp/shared-config` | Typed, validated env loader + config sections | **zero** |
| `@usrp/shared-events` | Envelope/correlation, topic routing, EventBus (Kafka/in-mem) | kafkajs (prod bus only) |
| `@usrp/shared-http` | Minimal `node:http` transport: routing, JSON parsing, errors, health/readiness, graceful shutdown (ADR-005) | **zero** (Node built-ins only) |
| `@usrp/shared-database` | Drizzle schemas, migrations, RLS SQL, client | drizzle-orm, postgres.js |

`shared-database` is consumed as **source** (its `exports` point at `src/*.ts`, no
`dist`); the others build to `dist`. Import rules are documented at the top of
`shared-database/src/index.ts` (agency services import only their own schema
subpath).

## 12. Engineering Conventions

These are load-bearing. Match them.

- **Language/module:** TypeScript, **ESM** (`"type":"module"`, `.js` import
  specifiers on relative imports), `Node16` module resolution.
- **Ultra-strict TS is the real quality gate.** Every package/service enables
  `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `strict`, explicit
  return types. `tsc --noEmit` must be **zero-error** before commit. (Per-package
  ESLint is not yet wired; TS is the gate.)
- **Zero-dependency shared packages** where feasible — Node built-ins over npm.
- **Self-check discipline:** every increment ships a **runnable self-check** that
  proves it against real infrastructure before commit (see the RLS isolation proof
  and `identity-service/selfcheck/verify-slice.ts`). Prove it; don't assert it.
- **Hexagonal services:** framework-agnostic domain + ports; infrastructure in
  adapters; a composition root wires them. Business outcomes are return values;
  only bad input and infra faults throw.
- **Secrets never leak:** raw NID / PII / biometrics never enter logs, events, or
  return values.
- **Commits:** Conventional Commits (`feat`, `fix`, `test`, `chore`, scope in
  parens), imperative, explaining the *why*. One logical change per commit.

## 13. Local Development

**Prereqs:** Node ≥24, pnpm 9, Docker.

```bash
cd usrp
pnpm install
pnpm infra:up:tier1          # Postgres, Redis, MinIO, Kong, G2G mocks
pnpm infra:up:tier2          # Kafka backbone (needed for the event proofs)
pnpm bootstrap:db            # CANONICAL: db:migrate → rls/0001 → rls/0002 (idempotent)
pnpm typecheck               # source-correctness gate — must be zero-error
pnpm verify                  # THE proof gate — RLS isolation + all 7 selfchecks, live
```

`bootstrap:db` (`scripts/bootstrap-db.sh`) codifies the one correct provisioning
order — schema migration, then roles + FORCE'd RLS (`0001`), then audit-log
immutability (`0002`) — so nobody has to remember it. `verify`
(`scripts/run-selfchecks.sh`) runs every proof in the repo against live infra;
**CI runs the identical scripts** (`.github/workflows/ci-backend.yml`), so the
"prove it, don't assert it" contract is enforced on every change, not by hand.
See `docs/architecture/ci-quality-gate.md`.

**Infra tiers:** `tier1` = core data + gateway + mocks; `tier2` adds the heavier
stack (Kafka, etc.). Compose files in `infrastructure/docker/`.

**G2G mocks** (`infrastructure/docker/mocks/{nida,nesa,hec,rib}`) simulate the
government APIs. NIDA citizen fixtures are keyed by `HMAC('dev_nida_hmac_secret',
NID)`; known dev NIDs live in the mock's `data/citizens.json` generator (e.g.
`1200380123456789` = a 22-year-old eligible citizen).

**Env:** services load config via `@usrp/shared-config` (canonical names:
`DATABASE_URL`, `NIDA_BASE_URL`, `NIDA_HMAC_SECRET`, `NATIONAL_ID_HMAC_KEY`,
`PII_ENCRYPTION_KEY`, …). ⚠ `.env.example` currently uses some older names — see §15.

**Run the identity service** (with tier1 up), then hit it:

```bash
pnpm build                                    # compile packages + services to dist
PORT=3200 pnpm --filter @usrp/identity-service start   # node dist/main.js (prod runtime)
# (dev loop instead: pnpm --filter @usrp/identity-service start:dev  — tsx, no build)
curl localhost:3200/health
curl -X POST localhost:3200/v1/identities/verify \
  -H 'content-type: application/json' \
  -d '{"nationalId":"1200380123456789","channel":"WEB"}'   # → 201 CREATED
```

**Run a service self-check** — `selfcheck` (core slice) and `selfcheck:http`
(HTTP slice, drives a real socket). See `identity-service-slice.md` and
`identity-service-http-slice.md` for the exact commands.

## 14. Current Status & Roadmap

### Done
- **Foundations:** 5 ADRs; all 6 shared packages built; data layer verified against
  live PG16 (schemas, FORCE'd RLS, cross-agency isolation proven, PII round-trip).
- **First service slice — `identity-service`** (hexagonal): raw NID → internal
  hash → NIDA lookup (G2G-signed) → PII-encrypted `applicant_identities` row
  created as the system service → `NIDA_VERIFICATION_COMPLETED` emitted; failure
  paths audited. Proven end-to-end by a 20-assertion live self-check. This is the
  **service template**. See `docs/architecture/identity-service-slice.md`.
- **HTTP transport (ADR-005) — the platform now runs.** `@usrp/shared-http` (a
  zero-dep `node:http` substrate) gives services real ingress: routing,
  health/readiness, correlation-id propagation into the event trace, graceful
  shutdown. See `docs/architecture/identity-service-http-slice.md`.
- **Compiled production runtime.** `shared-database` emits a runtime `dist`
  (runtime → dist JS, types → src `.ts`), so services run as `node dist/main.js`
  with working graceful shutdown (§15).
- **Second service — `eligibility-service` age slice.** Hexagonal rule engine:
  `POST /v1/eligibility/age-check` reads the verified applicant's (encrypted) DOB
  as the system service, evaluates the category age band from `AGE_CRITERIA`,
  emits an `AUDIT_ENTRY` (derived age only — never the DOB). Proven by a
  22-assertion live self-check; runs compiled with graceful shutdown. **Confirms
  the template generalizes.** See `docs/architecture/eligibility-service-slice.md`.
- **Event backbone proven + event-driven eligibility.** Real Kafka round-trip
  through `KafkaEventBus`, and `APPLICANT_SUBMITTED` → eligibility age gate →
  `AUDIT_ENTRY` with the causal chain intact, all over a live broker — no
  synchronous coupling. Fixed four real tier2 Kafka defects in the process (host
  listener, missing `vetting.hec`, a topic-init that created nothing, and
  consumer-groups that could never form). See `docs/architecture/kafka-backbone-proof.md`.
- **NESA A-Level education gate — 2nd live G2G integration.** `POST
  /v1/eligibility/education-check` runs the identity-VERIFIED guard, does an
  HMAC-signed NESA results lookup over G2G (mirrors the identity→NIDA gateway
  template), evaluates the accepted-level + RCS ≥70%-science rule, and emits both
  `NESA_VERIFICATION_COMPLETED` and `AUDIT_ENTRY` (no PII). Fails closed; degree
  categories are rejected as HEC's job. Proven by a 26-assertion live self-check
  (real PG + NESA mock). Completes eligibility's age **and** education promise.
  See `docs/architecture/eligibility-education-nesa-slice.md`.
- **Immutable audit trail — `audit-service` (a new archetype: pure event sink).**
  Closed a real compliance gap: three services emitted `AUDIT_ENTRY` onto
  `audit.immutable` with **no consumer**, and the "immutable" `audit_log` was
  actually **mutable** (the immutability was a code comment, not enforcement).
  `0002_audit_immutability.sql` adds belt-and-suspenders — an INSERT+SELECT-only
  `usrp_audit_writer` role **and** a BEFORE UPDATE/DELETE/TRUNCATE trigger that
  refuses tampering even for the table owner. The service consumes
  `audit.immutable` and appends idempotently (`ON CONFLICT (kafka_event_id) DO
  NOTHING`); no business HTTP surface (the trail is written only off the
  backbone). Proven by a 24-assertion live self-check (capture, idempotency,
  immutability-bites-as-owner, no-PII) plus a live end-to-end capture of a real
  eligibility `AGE_ELIGIBILITY_PASSED`. Runs compiled with graceful shutdown.
  See `docs/architecture/audit-service-slice.md`.

### The frontier
Three services live and deployable; the event backbone works; eligibility spans
age **and** NESA-verified education; **every audit event is now durably captured
in an immutable trail**. Next increments:
1. **eligibility HEC degree gate:** degree verification via HEC (needs
   `nationalIdHash`, a new `HECVerifiedPayload` wire type) — and it **owns** the
   education-based age exceptions (`AgeCriteria.maxAgeExceptions`, +1/+2 yrs for
   university/specialist) → `HEC_VERIFICATION_COMPLETED`.
2. **identity-service over real Kafka:** publish from its `main.ts` run (bus is
   already env-selected) so identity→eligibility is fully event-chained.
3. **biometric-service:** 1:1 face match (populates `nidaMatchConfidence`).
4. **Containerize** a service (Dockerfile → first deployable image).
5. Fold each new service into the identity-service + shared-http pattern; keep the
   self-check discipline.

### Working method
Deliver **thin vertical slices** end-to-end through every layer, each with a
runnable self-check, over broad-but-shallow scaffolding. Progress lives in the git

## 15. Known Issues & Open Decisions

   the shared-config canon.

   `tsx` remains the dev-loop runtime (`start:dev`). drizzle-kit tooling is
   unaffected (it uses relative `./src` paths).

## 16. Glossary

- **NIDA / NESA / HEC / RIB** — Rwanda's National ID Agency / National Examination
  authority / Higher Education Council / Investigation Bureau (the G2G sources).
- **G2G** — Government-to-government API integration.
- **RLS** — PostgreSQL Row-Level Security (row visibility enforced in the engine).
- **BFF** — Backend-for-Frontend (per-agency read/composition layer).
- **CRDT** — Conflict-free Replicated Data Type (offline field-score sync).
- **C2PA** — Content provenance standard for document authenticity (ADR-004).
- **`nationalIdHash`** — the internal, system-wide applicant key (HMAC of the NID
  with USRP's private key). **Not** the NIDA-lookup hash (§7).
- **Vertical slice** — a thin path exercised through every layer, proven by a
  runnable self-check.
