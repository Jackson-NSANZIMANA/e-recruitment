# S01 — Officer lifecycle (backend)

**Phase 1 · backend · depends on S00** · Branch `feat/s01-officer-lifecycle` · Reserved: **ADR-036**, **`rls/0033_officer_lifecycle.sql`**

## Why
The permission model (ADR-031: eight posts, operation-level permissions, separation of duties) cannot be *operated*. Today the only ways to create an officer are the dev seeder and the one-time first-admin script, and nothing can assign a post, disable an account or end someone's access. The capability map's build order #1 says this "blocks operating ADR-031". S06 builds the screens on top of this session.

## What the code tells you
| Fact | Source |
|---|---|
| Account columns: `officer_id`, `login_handle`, `credential` (scrypt), `agency`, `roles text[]`, `status active\|disabled`, `created_at` | `rls/0010_officer_accounts.sql` |
| `usrp_iam_service` has **SELECT only**. Writes must go through operation-specific `SECURITY DEFINER` command functions owned by a NOLOGIN role, with the actor bound by a transaction-local setting. | the pattern of `rls/0027_campaign_command_functions.sql` |
| Officer bearer tokens last **1 hour** and cannot be revoked by design | `iam-service/src/config.ts`, ADR-016 |
| Browser sessions live in `public_core.edge_sessions`, with `subject_id`, `roles` (a **copy**), `revoked_at`, `revoked_reason`. The edge holds the bearer token; the browser never sees it. | `shared-database/src/schemas/edge-sessions.schema.ts` |
| Separation of duties is per application, enforced inside the transition transaction. Account administration cannot weaken it. | ADR-031 §4 |

## Design to implement (record it in ADR-036)
- **Operations**, agency-scoped from the principal (never from the body):

  | Operation | Purpose |
  |---|---|
  | `listOfficers` | handle, posts, status, created and last login; no credential |
  | `createOfficer` | handle, initial posts |
  | `assignOfficerPosts` | replace posts, with a reason |
  | `disableOfficer` / `enableOfficer` | with a reason |
  | `revokeOfficerSessions` | end all of an officer's browser sessions now |

- **Permissions** in `shared-auth/permissions.ts` (append-only): `officer.read`, `officer.create`, `officer.posts.assign`, `officer.disable`, `officer.sessions.revoke`, all granted to `agency_admin` only. They do **not** grant `campaign.*` or decision powers by themselves.
- **Guards**, enforced in the command function, not only in the service:
  - same agency only;
  - no self-modification of posts or status;
  - cannot disable the last active `agency_admin` of an agency;
  - `agency_admin` can be granted only by an existing `agency_admin` (and possibly not at all; owner decision);
  - unknown posts refused.
- **Access ends on the next request.** `disableOfficer` and `assignOfficerPosts` also revoke that officer's edge sessions (reason `ACCOUNT_DISABLED` / `POSTS_CHANGED`), because the session caches roles.

  The residual risk to document: an upstream bearer token already held *by the edge* stays valid for up to one hour, but no browser can present it once its session is revoked. IAM login already refuses `disabled` accounts; verify this with a proof.
- **Initial credential delivery** (owner decision). Default: `createOfficer` returns a **one-time activation code** (shown once, stored hashed, expires in 24h), and the officer sets their password through an `activateOfficer` operation. No plaintext password is ever generated by the server, stored, logged or emailed.
- **Audit:** every command stages one `AUDIT_ENTRY` (actor, target, action, reason) in the same transaction. Events are PII-free (handle is not PII here, but keep payloads minimal).
- **Rehearsal:** `tools/rehearsal` gains a `staff` step that creates each scenario's station officers **through these operations**, as the agency admin. The dev seeder remains for bootstrap only.
